Booking software migration checklist

A migration fails quietly, not loudly. The new system works, the old link still gets traffic, and three weeks later a client arrives for an appointment that exists in neither calendar.

Two weeks out: inventory what you are moving

Before touching the new system, list everything the old one holds. Not just the client names — the things that are easy to forget and expensive to lose.

ItemWhy it mattersFormat to request
Client recordsNotes, allergies, formulas, preferencesCSV with all custom fields, not just contact details
Future appointmentsAnything booked after switch dayDate, time, service, staff, client, deposit status
Deposits and prepaymentsMoney already taken for future visitsBalance report; decide whether to honour in the new system
Gift cards and packagesOutstanding liability you still oweCode, remaining value, expiry
Service menu and pricesRebuilding these is slower than it looksExport or screenshot every variant
Staff, hours and time offDrives availability and payrollPer-person rota for the next eight weeks
Message templatesWording you have already refinedCopy the text into a document

Ask for the export in writing and check it opens. A file that arrives as a PDF is not an export; it is a picture of your data.

One week out: rebuild, then verify

  1. Recreate the structure. Services, durations, buffers, staff, rooms, opening hours, holidays. Do this before importing clients, or the import will fail on unmatched fields.
  2. Import a small batch first. Fifty clients is enough to expose broken phone formats, duplicated records and lost notes. Fix the mapping, then import the rest.
  3. Set up money. Deposits, cancellation fees, tax, tipping and payouts. Test one charge and one refund end to end.
  4. Recreate the messages. Reminder timings, confirmation text, and the opt-out wording. Send each one to your own phone.
  5. Move future appointments. Enter them manually if the import cannot preserve staff and service together. For a busy week that is a few hours; for a broken import it is a month of complaints.
  6. Check the public booking page. Book from a phone on mobile data. Confirm the confirmation email and the calendar invite both arrive.

Switch day: run both systems, briefly

Keep the old system readable for two to four weeks. Not writable — readable. You need it to answer "when was her last colour" and to check whether a deposit was taken. Cancel the subscription only after that window closes.

On the day itself, do four things in this order:

  • Put a redirect or a clear notice on the old booking link. Do not leave a working form that writes to a calendar nobody checks.
  • Update every place the link appears: website, Google Business Profile, Instagram bio, email signature, printed cards, review replies.
  • Tell staff where to look and who to ask. One named person for the first week beats a group chat.
  • Print the day's appointments. A piece of paper is a legitimate fallback for the first morning.

The most common switch-day failure is not data loss. It is two live booking links, both accepting appointments, only one of which anyone reads.

First week: watch these five things

Check them daily rather than waiting for the month-end report.

  1. Double bookings. Look for two clients in one slot, especially where a buffer used to absorb overruns.
  2. Missing reminders. Compare sent messages against the day's appointments. A wrong sender ID can get messages filtered silently.
  3. Deposits that did not attach. Any appointment that should have a card on file and does not.
  4. Duplicate clients. The same person imported twice, with history split across two records.
  5. Staff workarounds. If someone is keeping a paper list "just in case", find out why. That is your real bug report.

Thirty days later: close the loop

Reconcile the first month's payments against payouts, confirm that gift cards and prepaid packages were honoured, and export the client list from the new system once. If that export is incomplete, you have found the problem while you still have leverage.

Then write down what you would do differently. The next migration — a second location, a new platform, a sale — will be easier for it. If you are moving from paper rather than another platform, migrating from pen and paper covers the parts that do not apply here, and client intake forms is worth rebuilding at the same time rather than importing as-is.
